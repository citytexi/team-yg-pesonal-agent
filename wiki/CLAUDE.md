# LLM Wiki Schema

이 문서는 LLM(Claude Code)이 위키를 운영하는 방식을 정의한 스키마다.
**위키 작업(ingest/lint/query 또는 `wiki/`·`raw/` 편집) 시 이 파일의 모든 규칙을 따를 것.**
위키와 무관한 작업에는 적용하지 않는다.
경로는 모두 저장소 루트 기준이다(예: `wiki/index.md`, `raw/`).

> **데이터 계약은 [`wiki/conventions.md`](conventions.md)가 정본이다.** `status` 의미·미결 상태
> 부정 매칭·근거 우선순위·⚠️/🔁 마커·의존 방향은 거기 있고, 이 문서는 그것을 **참조**한다
> (중복 서술 금지 — 두 곳에 두면 드리프트한다).
>
> 분리 이유: 이 파일은 **에이전트 지시**를 담고 있어 외부 소비자(다른 저장소 CI 등)가
> 프롬프트 오염을 막으려고 제거한다. 실제로 iOS 쪽 리뷰 CI가 `wiki/CLAUDE.md`를 `rm` 한다.
> 그래서 **읽는 쪽이 반드시 알아야 하는 규약은 이 파일이 아니라 `conventions.md`와 데이터
> 자체(프론트매터·인라인 마커)에 둔다.**

## 디렉토리 구조

```
raw/              ← 불변 원본. 절대 수정 금지. 읽기만 가능.
  assets/         ← 로컬 이미지 및 첨부파일
wiki/             ← LLM이 생성·관리하는 전체 위키
  templates/      ← 페이지 템플릿(source·concept·entity·synthesis-analysis·synthesis-lint)
                    스키마 산출물. lint의 고아·깨진링크·frontmatter 검사 대상에서 제외.
  script/         ← 검사 스크립트(check-status.py)
  index.md        ← 전체 페이지 카탈로그 (항상 최신 상태 유지)
  log.md          ← append-only 이력 로그
  overview.md     ← 위키 전체를 관통하는 살아있는 개요/논지 (핵심)
  entities/       ← 사람, 조직, 제품, 프로젝트 등 고유 엔티티
  concepts/       ← 개념, 용어, 기술, 이론 등 주제 페이지
  sources/        ← raw/ 원본별 요약 페이지
  synthesis/      ← 쿼리 결과, 분석, 비교표, lint 보고서
    open-questions.md  ← 미해결 모순·오픈 질문 추적
```

## 공통 규칙

1. **raw/ 불변**: `raw/`는 읽기 전용. 내용을 수정하거나 파일을 생성/삭제하지 않는다.

2. **Obsidian 링크**: 위키 **내부** 링크는 **항상 `[[파일명]]` 형식만 사용**한다.

   **의존 방향 (⚠️ 필수)** — 규약 본문은 [`conventions.md` §6](conventions.md).
   이 위키는 **플랫폼 비종속 정책 SoT**다. Android(`parfait/`)든 iOS든
   구현 문서는 위키를 참조하지만, **위키는 구현 문서를 참조하지 않는다.**
   - `concepts/`·`entities/`·`sources/`·`overview.md`·`open-questions.md`에서 구현 문서 링크 **금지**.
     (`index.md` 허브 포인터 1개만 예외 — 사람 탐색용)
   - 구현과의 상충·교차 기록은 링크가 아니라 **플랫폼 + 심볼 데이터**로 적는다.
     ✅ "Android 구현 `YGColorChipType`이 14종" / ❌ `[[parfait/architecture/design-system]]`
   - 이유: 위키가 특정 플랫폼 문서 트리에 종속되면 다른 플랫폼 저장소에서 재사용할 수 없다.
   - **반대 방향(구현 → 위키)에서는 이중 링크**를 쓴다 — 구현 문서는 Obsidian 밖에서도 열리므로
     `[[개념명]] ([link](상대경로.md))` 병기가 유효하다. 그 규약은 구현 문서 소관.
   - lint가 이 방향 위반을 기계 검사한다.
   - 경로(`[[wiki/entities/파일명]]`) 또는 서브폴더(`[[entities/파일명]]`) 접두사를 붙이지 않는다.
   - 파일명이 충돌할 때만 예외적으로 경로를 추가한다.
   - 파일명 규칙: 영문 kebab-case 기본. 단, **personal 도메인의 한국 인물·장소 등 고유명사는 한글 파일명 허용** (`[[이효리]]`, `[[서울]]`).

3. **YAML frontmatter**: 모든 wiki/ 파일에 아래 형식을 포함한다.
   ```yaml
   ---
   tags: [카테고리, 도메인태그]
   sources: [원본파일명.md]
   updated: YYYY-MM-DD
   ---
   ```
   `sources/` 페이지는 여기에 **`status` 필드가 추가로 필수**다 → [판본 상태](#판본-상태-status--필수).

4. **작업 완료 시**: 매번 `wiki/index.md`와 `wiki/log.md`를 업데이트하고,
   **`python3 wiki/script/lint.py`를 실행해 위반 0건을 확인한다.**
   사람이 "lint 돌려줘"라고 할 때까지 기다리지 않는다 — 그 사이 드리프트가 쌓인다.
   위반이 남으면 커밋 전에 고치거나, 못 고칠 이유를 보고한다.

5. **언어**: 사용자와 한국어로 대화하되, 위키 내용은 한국어로 작성.

6. **개인 데이터 정책 (⚠️ 이 저장소는 public remote)**:
   - 이 repo는 공개(public)다. 추적되는 모든 파일은 인터넷에 평문으로 노출된다.
   - **식별 가능한 개인정보는 절대 추적되는 `wiki/`에 커밋하지 않는다.** 실명·연락처(이메일/전화)·주소/위치·생년월일·건강·재무·계정/인증 정보 등.
   - 이런 콘텐츠는 반드시 `wiki/personal-private/`(`.gitignore`로 추적 제외)에 저장한다.
   - 추적되는 `wiki/`에는 공개돼도 무방한 일반 지식·비식별 콘텐츠만 둔다.
   - `personal` 태그 페이지를 만들 때는 기본적으로 `wiki/personal-private/`에 생성하고, 공개 가능함이 명확한 경우에만 추적 영역으로 옮긴다.
   - 커밋 전 항상 lint를 돌려 민감정보 노출을 점검한다. 발견 시 커밋을 중단하고 사용자에게 보고한다.

## 근거 우선순위 (⚠️ 모든 워크플로우 공통)

규약 본문은 [`conventions.md` §1](conventions.md)에 있다. 작업 시 그 순서대로 읽는다 —
`index.md` → `concepts/`·`entities/` → `open-questions.md`(**필수**) → 필요 시 `sources/`.

**금지**: 근거를 `sources/`로 한정하거나 `sources/`를 `concepts/`보다 우선하는 것.
컴파일 결과를 버리고 원본 조각에서 매번 재유도하는 것이며, 이 위키가 피하려는 방식이다.
동음이의(같은 용어·다른 맥락)는 concept 페이지가 분리를 담당한다 → [`conventions.md` §5](conventions.md).

## 판본 상태 (`status`)

필드 정의·부정 매칭·체인 규칙·index 투영 토큰은 [`conventions.md` §2](conventions.md)가 정본.
작업 시 지켜야 할 것:

- `sources/` 페이지를 만들거나 고칠 때 `status`를 반드시 채운다(누락 = 인용 금지 대상이 됨).
- 새 판본을 ingest하면 **직전 판본 1건만** `superseded`(또는 `partial` + `scope`)로 갱신한다.
- `index.md` 줄의 토큰을 프론트매터와 맞춘다. 검사는 `python3 wiki/script/check-status.py`.

## 페이지 생성 임계 기준 (granularity)

독립 페이지를 **만드는** 조건 (둘 중 하나 충족):
- 2개 이상의 소스에서 등장한다
- 단독으로 다시 참조할 가능성이 높다 (핵심 개념, 핵심 인물 등)

독립 페이지를 **만들지 않는** 조건:
- 한 소스에서만 1회 언급된 부수적 요소 → 관련 페이지 내 인라인 언급 + 백링크로 처리
- stub 수준(이름만 있고 내용이 없을 것이 확실한 경우)

## 워크플로우 1: ingest (인터랙티브)

트리거: 사용자가 `raw/` 경로의 파일 또는 텍스트를 하나씩 주입할 때.

### 단계

ingest는 **분석 → 생성 2단계**다. 읽자마자 파일을 쓰지 않는다 — 분석을 건너뛰면
대체 관계 누락·모순 미등록이 그대로 파일에 굳는다(배치 모드에서 특히).

1. **읽기**: 대상 파일을 읽는다. 이미지가 포함되어 있으면 텍스트를 먼저 처리하고, 필요한 이미지를 이후 단계에서 별도로 본다 (→ [이미지 처리 규칙](#이미지-처리-규칙) 참고).
2. **분석 (파일 쓰기 전, 필수 — 배치 모드도 생략 불가)**: 아래를 **먼저 글로 정리**한다.
   단일 모드면 이걸 사용자와 논의하고, 배치 모드면 기록만 하고 진행한다.
   - **엔티티·개념 후보**: 각각 [페이지 생성 임계 기준](#페이지-생성-임계-기준-granularity) 충족 여부
   - **판본 관계**: 이 소스가 무엇을 대체하는가 / 무엇에 의해 대체되는가.
     **범위가 일부면 무엇만인지**(→ `status`·`superseded_by`·`scope` 결정 근거)
   - **기존 위키와의 모순**: 어느 페이지의 어느 서술과 어긋나는가 (→ `open-questions` 등록 대상)
   - **해소되는 기존 미결**: `open-questions`에서 이 소스가 닫는 항목 + **하류 반영 대상 페이지**
   - **동음이의 위험**: 같은 용어가 다른 맥락에서 다른 규격을 갖게 되는가 (→ concept 페이지가 분리)
3. **sources/ 페이지 생성**: `wiki/sources/[파일명].md`에 요약 페이지를 작성한다.
4. **entities/ 업데이트**: 페이지 생성 임계 기준을 만족하는 엔티티만 페이지 생성 또는 병합.
   - 모순 발견 시: 해당 섹션에 `> ⚠️ [날짜] [[원본파일]] 과 상충` 마커 추가 **+ `open-questions.md`에 항목 등록**.
5. **concepts/ 업데이트**: 임계 기준을 만족하는 개념만 신규 생성 또는 업데이트.
6. **overview.md 갱신**: 이 소스가 현재 논지를 강화하거나 반박하면 `wiki/overview.md`를 업데이트한다.
7. **index.md 업데이트**: 새 페이지를 카탈로그에 추가.
8. **log.md 추가**: `## [YYYY-MM-DD] ingest | [원본 제목]` 형식으로 한 줄 기록.

### 워크플로우 1b: ingest (배치)

트리거: 사용자가 여러 소스를 한꺼번에 주입할 때 ("배치로", "한꺼번에" 등의 표현).

- 단계 2에서 **사용자와의 논의만 생략**한다. **분석 자체는 생략하지 않는다** — 소스별로 분석 결과를
  기록한 뒤 생성한다. (분석을 건너뛴 배치 ingest가 판본 관계·모순 누락의 주된 원인이다.)
- 전체 완료 후 요약 보고서를 사용자에게 한 번에 제공한다: "N개 소스 처리, M개 페이지 생성/업데이트, K건 모순 발견".
- 모순이나 불명확한 판단이 필요한 경우만 중간에 사용자에게 확인한다.

### 페이지 템플릿

템플릿은 `wiki/templates/`에 **파일로** 둔다(Obsidian에서 그대로 쓰기 위함). 여기 인라인 복제하지 않는다 — 두 곳에 두면 드리프트한다.

| 대상 | 템플릿 |
|---|---|
| `sources/` | `wiki/templates/source.md` |
| `concepts/` | `wiki/templates/concept.md` |
| `entities/` | `wiki/templates/entity.md` |
| `synthesis/` 분석·비교(query 산출물) | `wiki/templates/synthesis-analysis.md` |
| `synthesis/` lint 보고서 | `wiki/templates/synthesis-lint.md` |

공통 규약(템플릿이 강제하는 것):

- **frontmatter 필수** — `tags`·`updated`, `sources/`·`concepts/`·`entities/`는 `sources`도. `sources/`는 추가로 `status`.
- **본문 섹션 구성은 자유.** 페이지마다 주제가 달라서 섹션을 강제하면 빈 껍데기가 생긴다. 해당 없는 섹션은 **지운다.**
- 대신 아래 셋은 고정:
  - 말미 연결 섹션은 **`## 연관`** (`## 관련`·`## 참고` 쓰지 않는다)
  - 미확정 항목 섹션은 **`## 미결`** (`## 미해결` 쓰지 않는다) — 반드시 `open-questions.md` 등록 + 링크
  - 판본이 걸린 섹션 제목엔 **`(vX 현행, [[소스]])`** 표기
- 상충 인라인 마커: `> ⚠️ [YYYY-MM-DD] [[대상]] 와 상충 — 무엇이 어긋나는지 → [[open-questions]]`

## 워크플로우 2: query

트리거: 사용자가 위키 전체를 바탕으로 질문하거나 분석을 요청할 때.

### 단계

1. **index.md 읽기**: 먼저 `wiki/index.md`를 읽어 관련 페이지와 **각 소스의 정본/대체 표기**를 파악한다.
2. **관련 페이지 읽기**: [근거 우선순위](#근거-우선순위--모든-워크플로우-공통) 순서대로 읽는다 —
   `concepts/`·`entities/` → `open-questions.md`(필수) → 필요 시 `sources/`.
   폐기본(`🔁`)은 "당시엔 이랬다"를 말할 때만 인용하고, 현행 근거로 쓰지 않는다.
3. **출력 형식 선택**: 질문 성격에 따라 아래 형식 중 하나를 선택한다.
   - 일반 분석 → 마크다운 본문
   - 항목 비교 → 비교표 (마크다운 테이블)
   - 발표용 → Marp 슬라이드 (frontmatter에 `marp: true`)
   - 데이터 시각화 → matplotlib 코드 블록
4. **답변 작성**: 읽은 내용을 종합해 출처 링크를 포함한 답변을 제공한다.
5. **저장 여부 판단**: 재사용 가치가 있는 분석·비교 결과는 `wiki/synthesis/[주제].md`에 저장하고 `overview.md` 갱신 필요 여부를 판단한다.
6. **log.md 추가**: `## [YYYY-MM-DD] query | [질문 요약]` 형식으로 기록.

---

## 워크플로우 3: lint

트리거: 사용자가 "위키 상태 점검" 또는 "lint"를 요청할 때.

### 실행

**먼저 `python3 wiki/script/lint.py`를 돌린다.** 기계 검사(민감패턴·frontmatter·링크 무결성·
의존 방향·고아/약연결·raw 정합·출처 추적·status)는 이 스크립트가 결정적으로 수행한다.
매번 즉석 스크립트를 다시 짜지 않는다 — 그러면 회차마다 검사 범위가 달라진다.

그다음 스크립트가 못 하는 항목(모순 감지, 해소분 하류 반영, 데이터 공백, stale 서술)을 읽어서 판단한다.

### 점검 항목

1. **민감 데이터**: 이메일, 전화번호, API 키, 비밀번호 패턴 탐지.
   - **발견 시**: 자동 수정 금지. 사용자에게 파일명·줄 위치를 보고하고 처리 방법(삭제·마스킹·private 폴더 이동)을 확인한다.
2. **모순 감지**: 같은 주제를 다루는 페이지들 간 상충 내용 탐지 → `open-questions.md`에 미해결 항목 등록.
3. **고아·약연결 페이지**: 인바운드 링크 0건은 위반, 1건(대개 index만)은 참고 —
   개념망에 편입이 덜 된 신호라 연결처를 검토한다.
4. **링크 없는 언급**: 페이지 없이 언급만 되는 엔티티·개념 (→ 페이지 생성 권고 또는 임계 기준 미달이면 무시).
5. **데이터 공백**: 채울 수 있는 빈 영역 또는 조사 권고 주제.
6. **stale 정보**: 최근 원본과 모순되는 오래된 내용.
7. **판본 상태(`status`) 무결성**: **`python3 wiki/script/check-status.py`로 검사한다**(눈대중 금지).
   검사 내용:
   - **필드 누락**: `grep -L "^status:" wiki/sources/*.md` → 결과가 있으면 전부 위반.
   - **값 오류**: `status`가 `current`/`superseded`/`partial` 외의 값.
   - **필수 필드 누락**: `superseded`·`partial`인데 `superseded_by` 없음, `partial`인데 `scope` 없음.
   - **깨진 참조**: `superseded_by`·`supersedes` 대상 파일이 실재하지 않음.
   - **체인 종단**: `superseded_by`를 따라가면 반드시 `status: current` 페이지에 도달해야 한다.
     사이클이거나 중간에 끊기면 위반.
   - **역방향 정합**: `supersedes`가 있으면 상대 페이지의 `superseded_by`와 서로 맞아야 한다.
   - **index 투영 불일치**: 프론트매터 `status`와 `index.md` 줄의 토큰이 어긋남. 프론트매터가 정답.
   - 이 항목의 지적은 **자동 수정 가능**(민감 데이터와 달리). 수정 후 보고한다.
8. **출처 추적(provenance)**: `concepts/`·`entities/` 본문이 `[[소스]]`를 인용하면
   그 소스가 프론트매터 `sources:`에도 있어야 한다. 어긋나면 "이 소스가 개정될 때 어느 페이지를
   고쳐야 하나"를 역추적할 수 없다.
9. **의존 방향**: 정책 콘텐츠 페이지가 구현 문서(`parfait/` 등)를 링크하지 않는지
   (→ [공통 규칙 2](#공통-규칙)). 위반 시 플랫폼 + 심볼 데이터 서술로 바꾼다.

## 모순 해소 워크플로우 (open-questions.md)

`wiki/synthesis/open-questions.md`는 모순·미결 질문의 단일 추적 장소다.

항목 형식:
```markdown
### [YYYY-MM-DD] [주제 요약]
- **출처 A**: [[페이지A]] — 주장 요약
- **출처 B**: [[페이지B]] — 상충 주장 요약
- **상태**: 미해결 | 해소됨 | 보류
- **해소 메모**: (해소된 경우 어느 쪽이 옳고 왜인지)
```

ingest·lint에서 모순이 발견되면 이 파일에 항목을 추가한다.
해소되면 상태를 "해소됨"으로 바꾸고 관련 페이지에서 `⚠️` 마커를 제거한다.

### 상태값 판정 규칙

[`conventions.md` §3](conventions.md) 참고 — 상태는 자유 서술이고 **`해소됨`이 아닌 모든 항목은
미결**이다. 서술을 열거형으로 깎지 않는다.

## 이미지 처리 규칙

- raw/assets/ 에 저장된 이미지는 ingest 시 **텍스트 처리 후** 필요한 이미지만 별도로 본다.
- 단순 장식·배너 이미지는 건너뛴다.
- 이미지에 데이터·도표·텍스트가 포함된 경우 해당 이미지를 별도로 읽고 핵심 내용을 sources 페이지에 기록한다.
- **텍스트 전용 소스만 다루는 경우**: assets/ 폴더를 사용하지 않고, ingest에서 이미지 단계를 생략한다.

## 확장성 경로

현재는 `wiki/index.md` 파일 하나로 탐색을 지원한다.
- **~100개 소스 이하**: index.md 방식으로 충분.
- **100개 초과 시**: [qmd](https://github.com/tobi/qmd) (로컬 BM25+벡터 하이브리드 검색) 도입을 고려한다. CLI 또는 MCP 서버로 연결해 LLM이 직접 쿼리할 수 있다.

## log.md 구조

append-only. 새 항목은 파일 **끝에** 추가.

```
## [YYYY-MM-DD] ingest | 제목
## [YYYY-MM-DD] query | 질문 요약
## [YYYY-MM-DD] lint | 점검 완료, N건 발견
```

`grep "^## \[" wiki/log.md | tail -10` 으로 최근 10개 이력 확인 가능.
