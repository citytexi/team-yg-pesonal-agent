## 코드가 매일 바뀌는데 문서는 어제 것이다

지난 글에서 기획 문서를 흡수하는 LLM 위키를 만든 이야기를 썼다. 이번엔 그 위키를 참조하는 쪽, 안드로이드 구현 문서 이야기다.

같은 저장소의 `parfait/` 디렉토리에 구현 문서를 쌓고 있다. ADR 23건, 아키텍처 가이드 5건, 구현이 끝나 아카이브로 옮긴 설계 스펙 74건, 작업 계획 43건이다. 문서를 쓰는 것도 고치는 것도 LLM이다.

한 달쯤 굴리고 나니 걸리는 게 있었다.

기획 문서는 개정될 때 파일이 새로 생긴다. `v0.2` 옆에 `v0.3`이 놓이니까 뭔가 바뀌었다는 사실 자체는 눈에 보인다. 코드는 그렇지 않다. 어제 머지된 PR이 문서에 아무 흔적도 안 남긴다. 문서는 자기가 틀렸다는 걸 모르는 채로 계속 그 자리에 있다.

그러면 확인하면 되는데 확인하려면 전부 다시 읽어야 했다. 어디부터 봐야 하는지를 가릴 근거가 없으니 매번 처음부터 뒤졌고 회차마다 검사 범위가 달라졌다.

문서에 "이건 어느 시점의 코드와 대조한 내용인가"를 박아두고 그 이후 것만 감사하는 방식으로 풀었다.

---

### 구현 문서를 위키에서 떼어냈다

처음엔 구현 문서가 위키 안에 있었다. `wiki/parfait/`였다. 7월 13일에 저장소 루트로 떼어냈다.

떼어낸 이유는 정본이 다르기 때문이다.

위키는 기획이 정본이다. 기획 문서가 개정되면 위키가 따라간다. 플랫폼과는 무관해서 iOS가 붙어도 그대로 재사용된다. 반면 구현 문서는 안드로이드 코드가 정본이다. 규율에 이렇게 적어놨다.

```
SoT 우선순위(모순 시): 코드 > wiki > CLAUDE.md
```

구현 문서는 어떤 경우에도 코드보다 아래다. 코드와 문서가 다르면 문서가 틀린 것이다. 애초에 지는 쪽으로 정해둔 문서를 어떻게 유지할 것인가가 이 글의 주제다.

위키에서 쓰던 판본 체인(`status`·`superseded_by`)도 그대로 옮길 수 없었다. 문서 종류마다 수명이 다르기 때문이다.

| 종류 | 무엇을 적나 | 수명 |
|---|---|---|
| `adr/` | 왜 이렇게 결정했나 | 폐기돼도 남는다. 대체된 ADR도 지우지 않는다 |
| `architecture/` | 어떻게, 어디에 있나 | 상시 갱신. 코드를 따라간다 |
| `specs/` | 무엇을 만드나 | 구현되면 `archive/`로 옮긴다 |
| `plans/` | 어떤 순서로 하나 | 끝나면 `archive/`로 옮긴다 |

가장 잘 낡는 건 `architecture/`다. 나머지 셋은 시점이 박제된 문서라서 나중에 읽어도 "그때 그렇게 정했다"로 읽히는데 아키텍처 가이드는 항상 현재형으로 쓰인다. "이 컴포넌트는 여기 있고 이렇게 쓴다"가 어제 기준이면 읽는 사람이 없는 파일을 찾는다.

---

### 문서는 자기가 언제 틀렸는지 모른다

드리프트가 아무 데서나 생기는 건 아니다. 거의 항상 **문서를 검증한 뒤에 머지된 PR**에서 생긴다. 그 전 것은 이미 한 번 대조했으니까.

이 규칙은 쓸모가 있는데 쓰려면 "문서를 검증한 시점"을 알아야 한다. 그게 없었다.

frontmatter에 `updated` 필드는 있었다. 그런데 이건 문서를 마지막으로 **고친** 날이지 코드와 **대조한** 날이 아니다. 오타를 고쳐도 올라가고 링크를 하나 바꿔도 올라간다. 반대로 코드를 한참 대조해보고 고칠 게 없다고 판단하면 아무것도 안 올라간다. 대조 사실이 기록되지 않는다.

두 개념이 섞여 있으니 `updated: 2026-08-10`을 보고도 이 문서가 8월 10일의 코드와 맞다고 말할 수 없었다.

### 마지막으로 대조한 커밋을 문서에 박는다

`parfait/doc-baseline.md`를 만들었다. 실제로 이렇게 생겼다.

```markdown
# 문서-코드 검증 기준선 (Doc Baseline)

> parfait 문서(spec/plan/architecture/adr/open-questions)를 **어느 `develop` 커밋 기준으로
> 마지막 검증했는지** 기록하는 단일 출처(SoT).

## 현재 기준선
- **repo**: 앱 저장소 `develop`
- **커밋**: `86f0f6b0` (`Merge pull request #305 ...`)
```

날짜가 아니라 커밋 해시로 잡은 게 이 방식의 전부다.

- 날짜는 "그날 몇 시"가 모호하다. 같은 날 머지가 다섯 건이면 어디까지 봤는지 못 가른다
- 브랜치가 여럿이면 커밋 시각순과 머지순이 다르다. 날짜로 자르면 순서가 어긋난다
- 해시는 git이 범위 연산자로 바로 받는다. `<기준선>..origin/develop`이 그대로 감사 대상이 된다

기준선은 문서마다 두지 않고 저장소 전체에 하나만 뒀다. 문서 수만큼 해시를 관리하면 그 해시들부터 서로 어긋난다. 관리 대상을 늘리지 않으려고 만든 장치가 스스로 관리 대상이 되면 안 된다.

갱신할 때는 이력 표에 한 줄씩 쌓는다. 지금 48회차다.

---

### 전체 재감사 대신 delta만 본다

기준선이 생겼으니 감사 범위가 계산된다. 절차를 스킬 파일로 고정했다. 첫 줄에 이렇게 적혀 있다.

```
**전체 재감사 금지** — 기준선 이후 신규 머지 delta만 본다.
```

1편에서 lint 스크립트를 고정한 것과 같은 이유다. 매번 LLM이 알아서 범위를 정하게 두면 회차마다 다른 걸 본다.

```bash
git -C <앱 저장소> fetch origin develop
git -C <앱 저장소> log --oneline --merges <기준선>..origin/develop
git -C <앱 저장소> show --stat <merge-hash>
```

delta가 나오면 그 PR이 건드린 심볼을 문서와 대조한다. 관련 스펙의 `status`, 아키텍처 문서의 컴포넌트 인벤토리, 미결 목록의 "미머지" 항목이 대상이다. 코드는 워킹트리가 아니라 `git show origin/develop:<path>`로 읽는다. 로컬 체크아웃은 다른 브랜치일 수 있다.

구현이 끝난 스펙은 `archive/`로 옮기는데 여기에 잔손질이 하나 붙는다.

```
이동 시 상대링크 `../` → `../../` 보정(archive는 한 단계 깊음). 이동 후 링크 resolve 검증.
```

절차에 안 적어두면 매번 깨진다. 링크가 깨진 채로 머지되면 다음 회차에 그걸 고치는 작업이 또 생긴다.

마지막 단계가 기준선 갱신이다. 새 HEAD로 교체하고 이력에 한 줄 남긴다. 감사만 하고 기준선을 안 올리면 다음 회차가 같은 delta를 다시 본다.

### 서버는 남의 저장소라 기준선이 하나 더 필요했다

`parfait/api/`에는 서버 API 계약이 스냅샷돼 있다. 도메인 7건에 엔드포인트 28개다. 정본은 서버 코드고 이 디렉토리는 미러다.

여기가 앱 코드보다 위험하다. 앱 코드는 내가 바꾸니까 바뀐 걸 알지만, 서버는 남이 바꾸고 나한테 알려주지 않는다. 그래서 기준선을 하나 더 만들었다.

브랜치를 정하는 데서 한 번 걸렸다.

```markdown
### 왜 `main`인가
서버 저장소의 기본 브랜치가 `main`이고 기능 PR이 main으로 머지된다.
`develop`은 main을 주기적으로 끌어오는 쪽이라 **뒤처진다**.

⚠️ 앱 저장소는 `develop`을 추적한다. **두 저장소의 통합 브랜치 이름이 다르다.**
```

체계를 만들던 시점에 서버 `develop`에는 회원가입과 연도 조회 API가 아예 없었다. 앱이 바라볼 서버는 `main`에서 나온다. 저장소가 둘인데 통합 브랜치 이름이 서로 반대라서 이건 문서에 경고로 박아뒀다.

두 번째로 걸린 건 필터였다.

```
`git log --oneline <기준선>..origin/main`
— **`--merges` 필터를 쓰지 않는다.** 기능 PR이 squash로 들어와 merge 커밋이 아닐 수 있다.
```

앱 저장소는 머지 커밋이 남아서 `--merges`로 PR 단위를 뽑는 게 편했는데, 서버는 squash 머지라 머지 커밋이 없다. 같은 명령을 그대로 옮겼다가 실제로 한 라운드에서 delta 3건이 전부 squash인 걸 봤다. 필터를 걸었으면 "변경 없음"으로 보고하고 넘어갔을 것이다.

기준선이 둘이 되니 같은 파일을 두 절차가 건드리게 됐다. `api/*.md` 한 파일 안에 서버 계약 절과 안드로이드 대응 상태 절이 같이 있기 때문이다. 경계를 이렇게 갈랐다.

| 무엇이 바뀌었나 | 어느 절을 고치나 | 누가 |
|---|---|---|
| 서버 delta | 엔드포인트·요청/응답 필드·에러코드 | 서버 동기화 절차 |
| 앱 delta | `android_status`·Android 매핑 절 | develop 동기화 절차 |

`verified` 필드는 서버 계약 대조일로 못 박고 한쪽만 갱신하게 했다. 양쪽이 다 건드리면 이 필드가 무슨 날짜인지 다시 모호해진다. 앞에서 `updated`가 겪은 것과 같은 문제라서 같은 실수를 반복하지 않으려고 두 절차 문서에 같은 문장을 넣어뒀다.

서버 저장소는 read-only로 정했다. fetch만 하고 커밋도 브랜치도 만들지 않는다.

### 다섯 주 굴려서 뭐가 잡혔나

7월 13일에 분리해서 지금까지 커밋 239건, 앱 기준선 갱신 48회, 서버 기준선 갱신 10회다. 실제로 잡힌 것 중 셋을 적어둔다.

**1. 응답 키가 바뀌어 아직 머지되지 않은 브랜치가 조용히 망가졌다.**

서버가 응답 필드명을 `nametagChip`에서 `nameTagChip`으로 바꿨다. 내부 프로퍼티명은 그대로고 HTTP 응답 DTO 경계에서만 바뀐 정리성 커밋이었다.

`develop`은 그 필드를 아직 안 읽어서 무해했다. 문제는 머지 안 된 브랜치 하나가 그 필드를 옛 키에 `String? = null`로 읽고 있었다는 거다. 키가 안 맞으면 값이 그냥 `null`이 된다. 예외도 안 나고 로그도 안 남는다.

이건 코드를 실행해도 안 잡힌다. 그 브랜치는 실서버를 부른 적이 없다. 서버 커밋과 앱 브랜치를 나란히 놓고 읽어야만 보인다.

**2. 널이 사라지자 원래 있던 버그의 사정거리가 넓어졌다.**

앱 매퍼가 업로드 시각을 이렇게 읽는다.

```kotlin
recentImageUploadedAt?.let(Instant::parse)
```

서버는 오프셋 없는 로컬 날짜시각을 주는데 `Instant.parse`는 오프셋을 요구한다. 원래부터 틀린 코드였다. 다만 그 필드가 널일 때가 많았다. 널이면 파싱을 건너뛰니 증상이 잘 안 나왔다.

서버가 `COALESCE`로 값을 채워 비널로 만들었다. 우회로가 사라졌다. 그룹이 하나라도 있으면 목록 조회가 실패한다.

앱 코드는 한 줄도 안 바뀌었다. 남의 저장소 커밋 하나가 잠재 버그를 상시 버그로 바꿨다.

**3. 문서가 있지도 않은 브랜치를 기준으로 수치를 적고 있었다.**

디자인시스템 문서에 "develop 기준 13화면, 잔여 3파일"이라고 적혀 있었다. delta를 감사하다 수치가 안 맞아서 따라가 보니, 그 수치의 근거인 브랜치가 로컬에만 있었다. 리모트에도 없다.

기준선 대조가 아니었으면 못 잡았을 것이다. develop에 있다고 적힌 것이 develop에 없다는 건 develop을 실제로 조회해야 나온다.

고칠 때 지우지는 않았다. 수치를 브랜치 기준이라고 표기하고 develop 값을 병기했다. 그 작업이 없어진 게 아니라 아직 안 들어온 것이기 때문이다.

### 코드 주석에도 같은 문제가 있었다

문서에 기준선을 박고 나서 보니 코드 주석이 더 나빴다. 주석에는 기준선을 박을 자리가 없다.

서버 delta를 한 번 반영했더니 **하루 전에 쓴 주석 넷이 전부 거짓이 됐다.**

| 하루 만에 거짓이 된 주석 | 왜 |
|---|---|
| `서버가 그쪽엔 이 값을 주지 않아서다` | 서버가 주기 시작했다 |
| `토핑이 하나도 없으면 null` | 서버가 `COALESCE`로 값을 채웠다 |
| `계약 타입이 널 허용이라` | 서버가 비널로 좁혔다 |
| `오프셋이 붙은 절대 시점` | 애초에 사실이 아니었다 |

넷 다 문법은 멀쩡하고 컴파일도 되고 테스트도 통과한다. 그것만 고치는 작업을 따로 만들어야 했다.

공통점이 있다. 전부 **다른 컴포넌트의 현재 상태**를 기술한 문장이다. 서버가 무엇을 주는지, 다른 파일에 무엇이 있는지, 어느 화면이 아직 이 값을 안 읽는지 같은 것들이다.

반면 "왜 이 시간대를 붙이나"는 안 낡는다. 의도는 남고 상태는 변한다.

그래서 규약을 이렇게 정했다. 써야만 한다면 단정하지 말고 근거 문서를 가리킨다.

```kotlin
// 서버는 오프셋 없는 로컬 날짜시각을 주고 그 벽시계는 KST다(api/parfait-group.md 타임존 절).
// 오프셋을 안 붙이면 기기 타임존에 따라 다른 시점이 된다.
```

계약이 바뀌면 저 문서가 갱신되고 저 문서에는 기준선이 있다. 주석은 포인터라서 낡지 않는다.

이 규약을 처음 적용한 커밋이 정확히 반대 방향으로 실수했다. 애매한 주석을 전부 "상태 서술"로 분류해서 지웠고 리뷰가 두 건을 되살렸다. 이름이 비슷한 두 DTO를 통일해야 하나 오해할 자리, 그리고 어느 화면이 어느 필드를 쓰는지 적어둔 자리였다.

둘 다 상태 서술이면서 동시에 오해를 미리 막는 정보였다. 그래서 최소 보존선을 하나 더 뒀다. 지울 때 그 정보가 어느 문서에 살아 있는지 확인하고 없으면 문서로 먼저 옮긴 뒤 코드에 포인터를 남긴다. 코드에서 지웠는데 문서에도 없으면 그건 정리가 아니라 유실이다.

### 남은 문제

가장 큰 구멍은 기준선을 갱신하지 않으면 전부 무력화된다는 것이다. 갱신은 절차의 마지막 단계인데 그 절차를 시작하는 건 사람이다. 아무도 안 부르면 기준선은 몇 주 전 해시로 남는다.

- 그 상태에서 문서를 읽으면 검증된 내용이라고 착각하기까지 한다
- 검증 시점을 적어둔 것이 오히려 신뢰를 과하게 준다
- 1편의 라우팅 절에서 쓴 것과 같은 지점이다. 규칙을 문서에 적는 일과 매번 실행되게 만드는 일은 다르다

기계 검사도 없다. 위키에는 lint 스크립트가 있는데 구현 문서 쪽에는 없다. 기준선 해시가 실재하는 커밋인지, 아카이브로 옮긴 문서의 상대 링크가 resolve되는지 정도는 스크립트가 결정적으로 볼 수 있다. 아직 안 만들었고 지금은 전부 읽어서 판단한다.

문서 자체도 비대해졌다. `doc-baseline.md`가 319줄인데 그중 대부분이 "현재 기준선" 한 절이다. 회차마다 무엇이 바뀌었는지를 앞에 계속 이어 붙인 결과다. 다음 회차가 직전 상황을 알아야 해서 그렇게 했는데 그건 이력 표가 하는 일과 겹친다. 아직 안 정리했다.

미결도 계속 쌓인다. 구현 미결 238건 중 해소된 게 40건이다. 위키에서 쓴 것과 같은 말을 여기서도 하게 된다. 이 체계가 미결을 해결해주지는 않는다. 무엇이 안 맞는지 세어지게 만들어줄 뿐이다.

그래도 세어지는 것과 안 세어지는 것의 차이는 크다. 서버가 응답 키를 바꾼 날, 그 사실을 아는 채로 브랜치를 열 수 있었다.

다음 편에서는 이 문서들을 실제로 쓰는 순서, 설계 스펙에서 계획을 거쳐 TDD로 내려가는 루프를 쓸 예정이다.
