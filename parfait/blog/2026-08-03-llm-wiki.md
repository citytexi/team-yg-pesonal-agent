## 기획 문서가 계속 개정되는 프로젝트에서 LLM이 읽는 위키 만들기

사이드 프로젝트를 안드로이드로 구현하면서 기획 문서를 계속 들여다봐야 했다. 기능정의서는 v2에서 v6까지 개정됐고 화면별 정책서도 v0.1에서 v0.3까지 각자 따로 굴러갔다. 지금 원본 파일만 36건이다.

두 가지가 걸렸다.

파일명으로 판본 계열을 알 수 없었다. `G-001-토핑-정책-v0.1`의 규격을 대체한 건 `G-001-토핑-정책-v0.2`가 아니라 이름이 전혀 다른 `G-001-무한파르페-간격-정책-v0.2`였다. 파일 목록을 훑어서는 이 관계가 보이지 않는다.

LLM한테 물어보려면 원본을 통째로 읽혀야 했다. 컨텍스트 낭비도 문제지만 더 큰 건 폐기된 판본을 현행으로 인용하는 사고였다. v0.1과 v0.3이 같은 디렉토리에 나란히 있으면 LLM은 둘을 구분할 근거가 없다. 그럴듯한 상수를 하나 집어와서 "정책 준수"라고 판정한다.

원본과 위키를 분리하고 LLM이 원본을 흡수해서 유지하는 정책 위키를 만들어 해결해보고자 한다.

---

### repo 구성

저장소는 세 축이다.

| 경로 | 성격 | 누가 쓰나 |
|---|---|---|
| `raw/` | 정책 원본. 불변, 읽기 전용 | 사람이 넣기만 함 |
| `wiki/` | `raw/`를 흡수해 만든 정책 지식 위키 | LLM이 생성·유지 |
| `parfait/` | 안드로이드 구현 문서(ADR·architecture·spec·plan) | LLM이 생성·유지 |

이 글은 가운데 `wiki/` 이야기다. `parfait/`는 다음 편에서 다룬다.

---

### raw는 왜 불변인가

```
raw/              ← 정책 원본. 수정·삭제 금지
wiki/
  index.md        ← 전체 카탈로그
  log.md          ← append-only 이력
  overview.md     ← 위키 전체를 관통하는 논지
  conventions.md  ← 데이터 계약
  sources/        ← raw 원본별 1:1 요약
  concepts/       ← 여러 소스를 종합한 개념 페이지
  entities/       ← 제품·조직 등 고유 엔티티
  synthesis/      ← 분석 결과, lint 보고서, open-questions
```

`raw/`를 읽기 전용으로 못 박은 이유는 대조 근거를 남기기 위해서다.

- 위키 서술이 의심스러울 때 돌아가서 확인할 원문이 필요하다
- LLM이 요약하다 틀렸는지, 원본 자체가 틀렸는지 구분하려면 원본이 그대로 있어야 한다
- 원본을 고치기 시작하면 "그때 기획이 뭐였나"를 복원할 방법이 없어진다

그래서 `sources/`가 원본 1:1 요약층으로 따로 있다. `raw/기능정의서-v6.md` 하나에 `wiki/sources/기능정의서-v6.md` 하나가 대응한다. 이 대응은 나중에 스크립트가 검사한다.

---

### 요약층만으로는 부족하다

처음엔 `sources/`만 있으면 될 줄 알았다. 원본별 요약이 있으니 LLM이 그것만 읽으면 컨텍스트가 줄어든다는 계산이었다.

그런데 요약을 아무리 잘 해도 안 풀리는 게 있었다. 같은 용어가 화면마다 다른 규격을 갖는 경우다.

`토핑`이라는 용어가 두 문서에 나오는데, 규격이 서로 다르다.

| 맥락 | 문서 | 규격 |
|---|---|---|
| 캔버스 배치 | C-106 | 초기 가로 40%, 정중앙, 48px 최소 터치, 캔버스 경계 클리핑 O |
| G-001 그리드 컴포넌트 | 간격 정책·설계서 | 프레임 160×160, Img 96×96, 6타입 회전 상수, 프레임 오버플로우 조항은 미확정 |

소스 페이지만 읽으면 이건 상충으로 보인다. 실제로는 애초에 같은 규칙이 아니다. 경계가 다른 별개 맥락이다. 한쪽 상수를 다른 맥락에 이식하고 정책을 지켰다고 판정하면 오답이다.

이런 맥락 분리를 담당하는 층이 `concepts/`다. 여러 소스를 종합해서 "이 용어는 맥락에 따라 이렇게 갈린다"를 적어둔다.

읽는 순서도 규약으로 박아뒀다.

```
index.md → concepts/·entities/ → open-questions.md → 필요할 때만 sources/
```

- 근거를 `sources/`로 한정하는 걸 금지했다
- 컴파일 결과(`concepts/`)를 버리고 원본 조각에서 매번 다시 유도하는 방식이 되기 때문이다
- 신뢰도는 파일 위치가 아니라 (판본 상태 × 적용 맥락)으로 결정된다

### 판본을 프론트매터에 박는다

본론이다. 도입에서 말한 첫 번째 문제, 파일명으로 계열을 알 수 없는 것을 여기서 푼다.

`sources/` 페이지 프론트매터에 판본 상태를 필수 필드로 넣었다.

```yaml
---
tags: [source, product]
sources: [G-001-토핑-정책-v0.1.md]
updated: 2026-07-13
status: superseded
superseded_by: [G-001-무한파르페-간격-정책-v0.2]
---
```

```yaml
---
tags: [source, product]
sources: [G-001-무한파르페-간격-정책-v0.2.md]
updated: 2026-07-27
status: superseded
superseded_by: [G-001-무한파르페-간격-정책-v0.3]
supersedes: [G-001-무한파르페-간격-정책-v0.1, G-001-토핑-정책-v0.1]
---
```

```yaml
---
tags: [source, product]
sources: [G-001-무한파르페-간격-정책-v0.3.md]
updated: 2026-07-27
status: current
supersedes: [G-001-무한파르페-간격-정책-v0.2]
---
```

세 파일을 이으면 `토핑-정책-v0.1 → 간격-정책-v0.2 → 간격-정책-v0.3` 체인이 나온다. 파일명은 중간에 바뀌지만 체인은 안 끊긴다.

`status` 값은 셋뿐이다.

- `current`: 지금 따라야 할 판본
- `superseded`: 전면 폐기본
- `partial`: 일부만 대체됨. 살아 있는 범위를 `scope`에 자유 서술로 적는다

설계하면서 정한 것 두 가지가 나중에 값을 했다.

**판정을 부정 매칭으로 했다.** `status: current`가 아닌 모든 소스는 현행 근거가 아니다.

- `superseded` 문자열을 찾는 방식을 쓰지 않았다
- 필드 누락, 오타, 나중에 추가될 새 값이 전부 "현행"으로 새기 때문이다
- `status`가 아예 없으면 판정 불가이므로 현행이 아니다. 실수로 필드를 빠뜨린 페이지가 조용히 인용되는 걸 막는다

**`superseded_by`는 최신 정본이 아니라 직후속 1개를 가리킨다.**

- 최신본을 가리키게 하면 새 판본이 나올 때마다 과거 페이지를 전부 고쳐야 한다
- 직후속만 가리키면 새 판본이 나와도 직전 페이지 1건만 갱신하면 된다
- 현행 판본은 체인을 따라가서 얻는다. 체인은 반드시 `current`에서 끝나야 하고 이건 스크립트가 검사한다

`index.md`에도 판본 상태를 표기하지만 거기는 투영이다. 단일 진실은 프론트매터고 둘이 어긋나면 프론트매터가 정답이다. 이것도 스크립트 검사 대상이다.

### 미결은 파일 하나로 추적한다

기획 문서끼리 모순되는 일이 계속 생겼다. 디자인 파일과 정책서가 다르거나, 정책서 두 건이 같은 값을 다르게 적거나, 아예 값이 안 정해진 채로 화면만 나온 경우다.

이걸 각 페이지에 흩어놓으면 "지금 확정 안 된 게 몇 건이냐"를 셀 수가 없다. `wiki/synthesis/open-questions.md` 하나로 모았다. 현재 26건이다.

```markdown
### [YYYY-MM-DD] 주제 요약
- **출처 A**: [[페이지A]] — 주장 요약
- **출처 B**: [[페이지B]] — 상충 주장 요약
- **상태**: 미해결 | 해소됨 | 보류
- **해소 메모**: 해소된 경우 어느 쪽이 옳고 왜인지
```

`상태`를 열거형으로 안 깎은 게 의도적이다. 실제로 쓰이는 값은 이렇다.

```
미해결
해소됨 (2026-07-29 당일, 풀 수집 후 실측)
미해결 (버전 정합)
미해결 (부분 해소 — ⑤ 닉네임 글자수·유효성 확정, 금칙어·중복만 잔존)
부분 해소 (①②④⑤ 해소·무효, ③ 잔존)
```

- 괄호 안 서술이 실제 알맹이다. 무엇이 남았는지가 거기 있다
- 열거형으로 깎으면 `부분 해소`가 `해소됨`이 되면서 잔존 항목이 사라진다
- 그래서 판정도 부정 매칭이다. `해소됨`으로 시작하지 않는 모든 항목은 미결이다
- `미해결` 문자열로 찾으면 `부분 해소 (…③ 잔존)` 같은 항목이 통째로 누락된다

확정 안 된 조항에는 본문에 인라인 마커를 단다.

```
> ⚠️ [2026-08-01] 디자인 파일과 상충 — Timestamp 색이 White vs Gray-200 → [[open-questions]]
```

`⚠️`가 붙은 조항은 현행 규칙이 아니다. 확정 대기 상태라서 근거로 인용하면 안 된다. 이 마커 하나로 "위키에 적혀 있으니 맞겠지"를 차단한다.

### 스키마를 프롬프트가 아니라 파일로 준다

LLM에게 이 규칙을 어떻게 전달할지가 문제였다. 매번 프롬프트에 붙이면 회차마다 내용이 달라진다. 그래서 `wiki/CLAUDE.md`에 스키마 파일로 두고 해당 디렉토리 파일을 열면 자동으로 로드되게 했다.

여기서 한 번 더 쪼갰다. 규약 문서를 둘로 나눴다.

| 파일 | 내용 | 성격 |
|---|---|---|
| `wiki/CLAUDE.md` | ingest·lint·query 워크플로, 단계별 지시 | 에이전트 지시 |
| `wiki/conventions.md` | `status` 의미, 부정 매칭, 근거 우선순위, 마커 해석 | 데이터 계약 |

쪼갠 이유는 이렇다. iOS 쪽에서 이 위키를 읽어갈 때 리뷰 CI가 `wiki/CLAUDE.md`를 `rm` 한다. 프롬프트 오염을 막으려는 조치라 그 자체는 타당하다. 그런데 데이터를 해석하는 규약이 거기 섞여 있으면 같이 날아간다. `status: superseded`가 무슨 뜻인지 모르는 채로 위키를 읽게 된다.

그래서 읽는 쪽이 반드시 알아야 하는 규약은 `CLAUDE.md`가 아니라 `conventions.md`와 데이터 자체(프론트매터, 인라인 마커)에 두기로 했다. `conventions.md`에는 에이전트 지시를 한 줄도 넣지 않았다. 외부 저장소가 sparse checkout으로 가져가서 그대로 신뢰해도 되는 유일한 문서다.

### 의존 방향은 구현에서 위키로 단방향

`parfait/`(안드로이드 구현 문서)를 만들고 나서 링크 방향 문제가 생겼다. 위키 개념 페이지에서 구현 문서를 링크하면 편하다. "이 정책은 여기서 이렇게 구현됨" 하고 바로 이어진다.

그러면 위키가 안드로이드 문서 트리에 종속된다. iOS 저장소가 `wiki/`만 체크아웃하는 순간 깨진 링크가 쏟아진다.

그래서 규약을 단방향으로 고정했다.

- `concepts/`, `entities/`, `sources/`, `overview.md`, `open-questions.md`에서 구현 문서 링크 금지
- `index.md`의 허브 포인터 1개만 예외로 뒀다. 사람이 탐색하려면 입구가 하나는 필요하다
- 구현 문서가 위키를 참조하는 반대 방향은 자유다

구현과 실제로 어긋나는 걸 발견했을 때는 링크 대신 플랫폼과 심볼을 데이터로 적는다.

```
❌ [[parfait/architecture/design-system]] 와 상충
✅ Android 구현 `YGColorChipType`이 14종 (정책은 12종)
```

링크가 없어도 어느 저장소의 어느 심볼인지 특정된다. iOS가 붙어도 위키는 그대로 재사용된다.

### 기계가 볼 수 있는 것은 기계가 본다

처음 몇 회차는 "위키 점검해줘" 하면 LLM이 그때그때 스크립트를 짜서 돌렸다. 문제는 회차마다 검사 범위가 달라진다는 거였다. 지난번에 잡던 걸 이번엔 안 잡는다.

결정적으로 돌아가는 항목만 골라서 `wiki/script/lint.py`에 고정했다. 180줄이다.

| # | 검사 | 잡는 것 |
|---|---|---|
| 1 | 민감 데이터 | 이메일·전화·자격증명·JWT·주민번호·절대경로 패턴 |
| 2 | frontmatter | `tags`·`updated` 누락, 콘텐츠 페이지의 `sources` 누락 |
| 3 | 링크 무결성 | `[[대상]]`이 실재하는지 |
| 4 | 의존 방향 | 정책 페이지가 구현 문서를 링크하는지 |
| 5 | 고아·약연결 | 인바운드 0건은 위반, 1건은 참고 |
| 6 | raw 정합 | 흡수 안 된 원본, 원본 없는 소스 페이지 |
| 7 | 출처 추적 | 본문이 인용한 소스가 프론트매터 `sources:`에도 있는지 |

7번이 은근히 중요했다. 개념 페이지 본문에서 `[[기능정의서-v6]]`을 인용했는데 프론트매터에 안 적혀 있으면, 나중에 그 소스가 개정될 때 어느 페이지를 고쳐야 하는지 역추적이 안 된다.

판본 상태 검사는 `check-status.py`로 따로 뺐다. 106줄이고 `lint.py`가 서브프로세스로 호출한다.

- 필드 누락, 값 오류, `superseded`인데 `superseded_by` 없음
- `superseded_by`·`supersedes` 대상 파일 실재 여부
- 체인 종단: `superseded_by`를 따라가면 반드시 `current`에 도달해야 한다. 사이클이거나 중간에 끊기면 위반
- 역방향 정합: `supersedes`가 있으면 상대 페이지의 `superseded_by`와 맞아야 한다
- `index.md` 투영 불일치

작성하면서 한 번 크게 헤맨 게 있다. 한글 파일명 링크가 전부 깨진 걸로 잡혔다.

```python
def nfc(s):
    return unicodedata.normalize("NFC", str(s))
```

macOS 파일 시스템은 파일명을 NFD로 저장한다. 한글이 자모 단위로 분리돼서 `pathlib`이 읽어온 파일명과 마크다운 본문에 적힌 `[[파일명]]`이 바이트 수준에서 안 맞는다. 눈으로는 똑같이 보인다. 파일명과 링크 대상을 전부 NFC로 정규화하고 나서야 맞았다.

코드 펜스와 주석 블록도 제거하고 검사한다. 템플릿 파일의 플레이스홀더나 예시 코드 안의 `[[대상]]`이 실제 링크로 잡히면 오탐이 계속 난다.

```python
LINK = re.compile(r"\[\[([^\]|#]+)(?:[|#][^\]]*)?\]\]")
COMMENT = re.compile(r"<!--.*?-->", re.S)
FENCE = re.compile(r"```.*?```", re.S)

def text(p):
    """주석 블록·코드 펜스를 제거한 본문 — 링크 검사는 항상 이걸 쓴다."""
    return FENCE.sub("", COMMENT.sub("", p.read_text(encoding="utf-8")))
```

두 스크립트 모두 위반이 있으면 종료 코드 1을 반환한다. 외부 CI에 그대로 걸 수 있다.

```bash
python3 wiki/script/check-status.py
python3 wiki/script/lint.py
```

### 라우팅은 아직 index.md 한 장이다

lint가 잡는 건 형식이다. 정작 매 작업에서 반복되는 건 "이번 질문에 어느 페이지를 읽힐 것인가"인데, 지금 여기를 담당하는 건 `index.md` 한 파일이다. 66개 페이지의 한 줄 요약이 거기 다 있고 스키마에는 필요한 페이지만 펼치고 전체를 읽지 말라고 적어놨다.

66건에서는 돌아간다. 문제는 카탈로그가 페이지 수만큼 길어진다는 거다. 페이지가 늘면 카탈로그를 읽는 비용이 페이지를 읽는 비용에 가까워진다.

같은 문제를 스킬 쪽에서 먼저 만났다. 벤더 스킬이 쌓이니까 목록만 봐서는 뭘 로드할지 못 골라서 검색 스크립트를 하나 짰다.

```python
def score(query, skill):
    q = set(tokenize(query))
    if not q:
        return 0.0
    name_t = tokenize(skill["name"])
    desc_t = tokenize(skill["desc"])
    head_t = tokenize(skill.get("headings", ""))
    total = 0.0
    for t in q:
        total += 4 * name_t.count(t) + 2 * desc_t.count(t) + 1 * head_t.count(t)
        if any(t in n for n in name_t):
            total += 1
    return total
```

72줄이고 stdlib만 쓴다. `SKILL.md` 프론트매터의 `description`과 본문 헤딩을 토큰으로 쪼개서 이름 일치 4점, 설명 일치 2점, 헤딩 일치 1점으로 매긴다. 부분 문자열 일치에 1점을 더 준 건 한국어 쿼리에 영문 스킬명이 섞여 들어오기 때문이다. 임베딩도 인덱스 파일도 없다. 스킬 수십 개 규모에서는 이걸로 충분했다.

위키에 그대로 옮기면 안 되는 이유가 하나 있다. 스킬은 서로 독립이라 점수 높은 순으로 몇 개 던져주면 되지만 위키 페이지는 판본 상태가 얽혀 있다. 점수가 제일 높은 페이지가 폐기본일 수 있다. 검색 결과에 `status`를 같이 싣지 않으면 앞에서 만든 안전장치가 통째로 무력해진다. 정렬을 `current` 우선으로 깔거나 최소한 결과마다 판본 토큰을 붙여야 한다.

읽는 순서 규약을 다시 보니 절반은 이미 하고 있었다. `concepts/`와 `open-questions.md`는 매번 읽고 `sources/`는 필요할 때만 연다는 규칙이 그거다. 반드시 읽을 문서와 필요할 때 열 문서를 갈라두는 접근인데, 나는 이걸 층 이름으로만 적어놨지 검색 결과에 등급으로 실어 보낸 적은 없다. 이 구분을 작업 단위로 명시하는 방법은 taehwandev 님 글에 정리돼 있다(아래 참고 링크).

더 큰 구멍은 따로 있다. 검색 스크립트를 만들어놔도 부르지 않으면 없는 것과 같다. 지금 위키 쪽에는 규약만 있고 실행을 강제하는 장치가 없다. lint는 작업이 끝난 뒤 결과를 검사할 뿐이라서, 작업을 시작할 때 라우팅을 거쳤는지는 아무도 확인하지 않는다. 규칙을 문서에 적는 일과 매번 실행되게 만드는 일은 다르다.

### 남은 문제

기계 검사가 커버하는 건 형식뿐이다. `lint.py` 마지막 줄에 이렇게 적어놨다.

```
> 모순 감지·해소분 하류 반영·데이터 공백·stale 서술은 기계 검사 밖 — 사람/LLM이 읽어야 한다.
```

- 두 페이지가 같은 값을 다르게 적고 있는지는 읽어야 안다
- 미결이 해소됐을 때 그걸 인용하던 페이지를 찾아 고치는 것도 읽어야 한다
- 기획이 아직 안 정한 빈칸을 찾는 것도 마찬가지다

이 셋은 여전히 매 회차 사람이나 LLM이 위키를 읽어야 한다. 검사 대상 68건 규모에서는 감당되지만 더 커지면 방법을 바꿔야 한다. 바로 앞에서 적은 라우팅 문제와 같은 지점에서 터질 것 같다.

미결 18건도 그대로 남아 있다. 위키가 이걸 해결해주지는 않는다. 확정 안 된 게 뭔지 세어지게 만들어줄 뿐이다. 그것만으로도 구현할 때 "이 값은 아직 미정입니다"라고 말할 수 있게 됐으니 목적은 달성했다고 본다.
