# open-questions → GitHub 이슈 동기화 설계

- 작성일: 2026-08-10
- 대상 저장소: `citytexi/team-yg-pesonal-agent` (이 repo)
- 산출물: 이슈 템플릿 4종, `parfait/script/oq_sync.py`, 스킬 `sync-open-questions`

## 배경

미결 항목은 지금 두 문서에 마크다운으로만 있다.

| 문서 | 소관 | 항목 수(2026-08-10) |
|---|---|---|
| `wiki/synthesis/open-questions.md` | 정책·기획 미결 | 25 |
| `parfait/synthesis/open-questions.md` | 구현·계약·정합 미결 | 111 |

계 136항목, 그중 `해소됨`이 24건이라 첫 실행의 `create` 대상은 112건이다.

> 참고: `grep -c '^### \['`로 세면 26/112(계 138)가 나온다 — 두 문서 말미의 "항목 추가
> 형식" 예시가 HTML 주석 안에 있는데, `grep`은 주석을 구분하지 못해 그 안의
> `### [YYYY-MM-DD] [주제 요약]`까지 각 문서 1건씩 헤딩으로 센다. 파서는 주석 내부를
> 제외하므로(파싱 규칙 2번) 실제 항목 수는 136이다.

문서 안에서만 살아 있어서 담당자 배정·알림·검색·상태 추적이 안 된다. 이 저장소의 GitHub
이슈는 현재 0건이다. 미결을 이슈로 투영하면 GitHub의 협업 표면(assignee·알림·검색·마일스톤)을
얻으면서 문서의 서술 밀도는 유지할 수 있다.

## 결정 사항

브레인스토밍에서 확정한 것:

1. **이슈 생성 대상 저장소는 이 repo 하나.** wiki 계열·parfait 계열 모두 여기로 모은다.
   TJYG-Android에는 만들지 않는다.
2. **문서가 정본, 이슈는 단방향 투영.** 이슈 본문을 손으로 고쳐도 다음 동기화에서 덮어쓴다.
   이슈 → 문서 역주입은 하지 않는다.
3. **매칭 키는 문서에 부여한 안정 ID.** 제목 해시가 아니다.
4. **템플릿은 open-question + 일반 세트.**
5. **실행 게이트는 dry-run 후 일괄 승인.** 항목별 승인이 아니다.
6. **`해소됨`이면 해소 메모를 코멘트로 남기고 close.**
7. **투영 범위는 전량 미러.** `해소됨`으로 시작하지 않는 모든 항목을 이슈로 만든다.
   보류·부분 해소도 만든다. 라벨로만 구분한다.

7번의 근거: 두 문서가 공유하는 규약이 "**`해소됨`으로 시작하지 않는 모든 항목은 미결**"이라는
부정 매칭이다. 이슈 쪽에서 `보류`를 걸러내는 등 다른 필터를 쓰면 두 기준이 갈라지고, 그 드리프트가
바로 이 도구가 없애려는 문제다.

## 문서 형식 (파싱 대상)

두 문서의 항목 형식은 동일하다.

```markdown
### [2026-07-10] YGButton 디자인 토큰 규칙 미확정
- **출처**: `component/ygbutton/YGButtonType.kt` — ...
- **항목**: ① ... ② ...
- **상태**: 미해결
- **해소 메모**: ...
```

필드 이름은 문서마다 조금 다르다. wiki는 `출처 A`/`출처 B`를 쓰고 parfait는 `출처` 단수를 주로
쓴다. 파서는 필드 이름을 열거형으로 강제하지 않고 **`- **이름**: 값` 형태를 전부 보존**한다.
필드가 늘어도 스크립트를 고칠 필요가 없다.

### 파싱 규칙

1. 항목 = `### [YYYY-MM-DD] 제목` 헤딩과 다음 `###` 헤딩(또는 EOF) 사이.
2. **HTML 주석(`<!-- ... -->`) 내부는 제외.** 두 문서 말미에 "항목 추가 형식" 예시가 주석으로
   들어 있고, 그 안에 `### [YYYY-MM-DD] [주제 요약]`과 `- **상태**: 미해결 | 해소됨 | 보류`가
   있다. 제외하지 않으면 유령 항목이 생긴다.
3. 헤딩의 날짜는 `발견일`로 보존한다. 정렬·표시에만 쓰고 매칭에는 쓰지 않는다.
4. 제목에 `**`·백틱 등 인라인 마크다운이 있어도 그대로 둔다. 이슈 제목에서만 정리한다.

## ID 스킴

- 형식: `OQ-W-###`(wiki) / `OQ-P-###`(parfait). 3자리 zero-pad. 999 초과 시 자리수를 늘린다.
- 부여 순서: 문서 등장 순.
- **헤딩은 건드리지 않는다.** ID는 항목 본문 첫 필드로 넣는다.

```markdown
### [2026-07-10] YGButton 디자인 토큰 규칙 미확정
- **ID**: OQ-P-001
- **출처**: ...
```

헤딩을 고치면 앵커가 깨진다. parfait 문서는 실제로 문서 내부에서
`[2026-08-01 줌 死코드 항목](#2026-08-01-카메라-줌-ui가-死코드로-남음)` 같은 앵커 참조를 쓰고 있고,
다른 parfait 문서들도 이 파일의 항목을 앵커로 가리킨다. 헤딩 무변경이면 기존 링크가 전부 살아
있다.

- ID는 한 번 부여하면 **불변**이다. 제목이 바뀌어도, 날짜가 정정돼도 유지한다.
- 항목을 삭제해도 **번호를 재사용하지 않는다.** 다음 번호 = 문서 내 최대값 + 1.
  (닫힌 이슈가 다른 항목으로 되살아나는 사고를 막는다.)

## 이슈 형태

### 제목

```
[OQ-P-001] YGButton 디자인 토큰 규칙 미확정
```

제목에서 인라인 마크다운(`**`, 백틱)은 제거한다. 256자를 넘으면 자르고 `…`를 붙인다.

### 본문

```markdown
<!-- oq-id: OQ-P-001 -->
<!-- oq-hash: 8f2a1c0d3e5b -->
<!-- oq-source: parfait/synthesis/open-questions.md -->

> 정본은 문서다. 이 이슈는 문서의 투영이며, 문서가 바뀌면 이 본문은 덮어써진다.
> 여기서 고친 내용은 문서에 반영되지 않는다.
> 원본: [parfait/synthesis/open-questions.md](https://github.com/citytexi/team-yg-pesonal-agent/blob/main/parfait/synthesis/open-questions.md#2026-07-10-ygbutton-디자인-토큰-규칙-미확정)

**발견일**: 2026-07-10

- **출처**: `component/ygbutton/YGButtonType.kt` — ...
- **항목**: ① ... ② ...
- **상태**: 미해결
- **해소 메모**: ...
```

문서 항목 본문을 **요약하지 않고 그대로** 옮긴다. 요약하면 이슈만 본 사람이 잘못된 결론에 이르고,
요약 규칙 자체가 유지보수 대상이 된다.

`- **ID**:` 줄은 본문에서 제외한다(제목·마커에 이미 있다).

원본 링크는 `https://github.com/<owner>/<repo>/blob/main/<경로>#<앵커>` 절대 URL로 만든다.
이슈 본문에서 상대 링크는 resolve 기준이 불안정하다. `owner`/`repo`는 `gh repo view`로 얻는다.
브랜치가 main에 머지되기 전에는 링크가 404일 수 있고, 이는 의도된 것이다 — 정본은 main이다.

### 앵커 생성

GitHub 헤딩 slug 규칙을 따른다.

1. 헤딩 텍스트에서 `#` 제거 후 trim
2. 소문자화
3. 영숫자·하이픈·언더스코어·유니코드 문자를 제외한 문자 제거(`[`, `]`, `·`, `.`, `(`, `)` 등)
4. 공백을 `-`로 치환

`### [2026-08-01] 카메라 줌 UI가 死코드로 남음` → `2026-08-01-카메라-줌-ui가-死코드로-남음`.
문서에 이미 쓰이고 있는 앵커와 일치하는지 테스트로 고정한다.

### 마커

| 마커 | 용도 |
|---|---|
| `oq-id` | 짝짓기 키. 제목·본문이 바뀌어도 유지 |
| `oq-hash` | 문서 항목 본문의 정규화 해시. 다르면 갱신 대상 |
| `oq-source` | 원본 문서 경로. 계열 판정·링크 생성용 |

`oq-hash`가 delta 판정의 핵심이다. 없으면 매 실행마다 120건을 전부 다시 쓴다.

**정규화 규칙** — 흔들리면 매번 전건 갱신이 뜬다:

1. 항목 본문(헤딩 제외, 다음 헤딩 전까지)을 대상으로 한다
2. `- **ID**:` 줄 제거
3. 각 줄 오른쪽 공백 제거
4. 빈 줄 제거
5. 남은 줄을 `\n`으로 join
6. UTF-8 SHA-256의 앞 12자(hex)

줄 끝 공백·문단 사이 빈 줄 추가는 해시를 바꾸지 않는다. 실제 내용이 바뀌면 바뀐다.

### 라벨

계열 라벨과 상태 라벨을 병행한다.

| 라벨 | 색 | 의미 |
|---|---|---|
| `oq:wiki` | `#0075ca` | 정책·기획 미결 |
| `oq:parfait` | `#5319e7` | 구현·계약 미결 |
| `oq:open` | `#d73a4a` | 미결 |
| `oq:partial` | `#fbca04` | 부분 해소 — 잔존 항목 있음 |
| `oq:blocked` | `#cfd3d7` | 보류 |
| `oq:resolved` | `#0e8a16` | 해소됨(closed) |

상태 라벨은 문서 상태 문자열에서 **접두 규칙**으로 판정한다. 상태는 자유 서술이므로
정확 일치가 아니라 접두·포함으로 본다.

| 조건(순서대로 평가) | 액션 | 상태 라벨 |
|---|---|---|
| `해소됨`으로 시작 | close + 해소 메모 코멘트 | `oq:resolved` |
| `부분 해소` 포함 | open 유지, 본문 갱신 | `oq:partial` |
| `보류`로 시작 | open 유지 | `oq:blocked` |
| 그 외 전부 | open 유지 | `oq:open` |

`부분 해소`를 `보류`보다 먼저 평가한다. `미해결 (부분 해소 — ⑤ …)`처럼 접두는 `미해결`이지만
부분 해소인 항목이 실재한다.

**상태 라벨은 라벨일 뿐 투영 여부를 바꾸지 않는다.** `보류`도 이슈를 만든다(결정 7).

라벨이 저장소에 없으면 `apply`가 만든다.

## 스크립트 `parfait/script/oq_sync.py`

`parfait/script/README.md` 규약을 따른다. stdlib 전용, `python3 parfait/script/oq_sync.py`,
repo 루트 = `Path(__file__).resolve().parents[2]`, 테스트는 같은 디렉토리 `test_oq_sync.py`.

GitHub 접근은 `gh` CLI를 `subprocess`로 호출한다(토큰 취급을 직접 하지 않는다).

### 서브커맨드

| 커맨드 | 하는 일 | 리모트 |
|---|---|---|
| `assign-ids` | ID 없는 항목에 ID 부여, 문서 in-place 수정 | 접근 안 함 |
| `plan` | 문서 파싱 + 기존 이슈 대조 → 계획 산출 | 읽기만 |
| `apply <plan.json>` | 계획대로 이슈 생성·수정·close·reopen | **쓰기** |

`plan`/`apply` 분리가 dry-run 게이트의 실체다. 스킬의 문장이 아니라 스크립트 구조가 강제한다.

#### `assign-ids`

- 두 문서를 읽고 `- **ID**:` 없는 항목에 다음 번호를 부여한다
- **멱등**: 두 번 돌려도 결과가 같다. 이미 ID가 있으면 건드리지 않는다
- 헤딩 바로 다음 줄에 `- **ID**: OQ-X-###`를 삽입한다
- `--check` 옵션: 수정하지 않고 미부여 항목 수만 보고, 있으면 종료 코드 1
- 출력: 새로 부여한 ID 목록

#### `plan`

1. 두 문서를 파싱해 항목 목록을 만든다(ID 없는 항목이 있으면 에러로 중단 — `assign-ids` 먼저)
2. `gh issue list --state all --limit 1000 --json number,title,body,state,labels`로 기존 이슈를
   가져온다. 본문 `oq-id` 마커로 인덱싱한다.
   `--label`을 여러 번 주면 gh는 **AND**로 묶으므로 `oq:wiki`와 `oq:parfait`를 동시에 걸면
   결과가 0건이 된다. 라벨로 거르지 않고 전량을 받아 마커로 판별한다
3. 대조해서 액션을 정한다

| 문서 | 이슈 | 문서 상태 | 액션 |
|---|---|---|---|
| 있음 | 없음 | `해소됨` 아님 | `create` |
| 있음 | 없음 | `해소됨` | `skip` (해소된 걸 새로 만들지 않는다) |
| 있음 | open | 해시 동일 + 라벨 동일 | `noop` |
| 있음 | open | 해시 다름 | `update` |
| 있음 | open | `해소됨` | `close` |
| 있음 | closed | `해소됨` 아님 | `reopen` (+ 필요 시 `update`) |
| 있음 | closed | `해소됨` | `noop` |
| 없음 | open | — | `orphan` (보고만, 자동 close 안 함) |

`orphan`은 문서에서 항목이 사라진 경우다. 삭제 의도인지 실수인지 도구가 판단할 수 없으므로
**자동으로 닫지 않고 사람에게 보고**한다.

`open-question.yml` 템플릿으로 손수 만든 이슈는 `oq-id` 마커가 없다 → `unmanaged`로 분류해
별도 보고한다. 문서에 옮길지는 사람이 정한다.

같은 `oq-id`가 여러 OPEN 이슈에 걸쳐 있으면(예: 수동 재생성) 이슈 번호가 가장 작은 것
(먼저 만들어진 것)을 문서 항목의 짝으로 삼고, 나머지는 `duplicate`로 보고한다. `orphan`과
같은 철학으로 자동으로 닫지 않는다 — 정리는 사람이 한다.

4. 출력: 사람이 읽는 표(stdout) + 계획 JSON 파일

```json
{
  "repo": "citytexi/team-yg-pesonal-agent",
  "summary": {"create": 112, "update": 0, "close": 0, "reopen": 0, "noop": 0, "orphan": 0, "unmanaged": 0, "duplicate": 0},
  "actions": [
    {"action": "create", "oq_id": "OQ-P-001", "title": "...", "body": "...", "labels": ["oq:parfait", "oq:open"]},
    {"action": "close", "oq_id": "OQ-W-003", "issue": 42, "comment": "..."}
  ]
}
```

시각 값(`generated_at` 등)은 넣지 않는다 — 계획을 다시 산출할 때마다 값이 바뀌어 diff
노이즈만 만들고, 매칭·비교 로직 어디에서도 쓰이지 않는다.

계획 JSON은 스크래치패드에 쓴다(저장소에 커밋하지 않는다).

#### `apply`

- 계획 JSON을 읽어 순차 실행한다
- 시작 전에 `plan.repo`와 `gh repo view`로 얻은 현재 repo를 대조한다. 다르면 즉시 중단한다
  (다른 저장소에서 뜬 계획이 그대로 실행되는 사고를 막는다)
- 필요한 라벨이 없으면 먼저 만든다
- **항목 단위 멱등**: 중간에 실패해도 `plan`을 다시 돌리면 남은 것만 잡힌다
- 쓰기 액션 사이 `WRITE_INTERVAL_SEC`(기본 1초)만큼 대기하고, 연속 실패가
  `MAX_CONSECUTIVE_FAILURES`(기본 5)건에 도달하면 남은 액션을 실행하지 않고 중단한다
  (GitHub 2차 rate limit — 콘텐츠 생성 분당 약 80건 — 을 계속 두드리는 것을 막는다)
- 실패는 삼키지 않는다. 실패 목록을 마지막에 출력하고 종료 코드 1
- `--limit N`으로 실행 건수를 제한할 수 있다(첫 실행을 나눠 받고 싶을 때)
- 진행 상황을 건별로 출력한다(112건이 조용히 도는 것을 막는다)

**같은 계획 파일을 두 번 실행하지 않는다.** 계획 파일 자체에는 실행 이력이 없다 —
`--limit`으로 나눠 받거나 실패 후 재실행할 때 같은 계획 파일을 다시 `apply`하면 이미 만든
이슈를 또 만든다. 그래서 `apply`는 실행이 끝나면 계획 파일 옆에 `<plan>.applied` 마커
파일을 남기고, 마커가 있는 계획으로 다시 `apply`를 시도하면 종료 코드로 즉시 중단한다
(우회 옵션 없음). 나눠 받거나 실패 건이 있으면 다음 배치 전에 반드시 `plan`을 다시
산출해 새 계획 파일을 만든다.

## 이슈 템플릿 `.github/ISSUE_TEMPLATE/`

| 파일 | 용도 |
|---|---|
| `open-question.yml` | 미결 항목 수동 등록 |
| `bug.yml` | 스킬·스크립트·문서 오류 |
| `task.yml` | 문서 작업·개선 요청 |
| `config.yml` | blank 이슈 허용 + 안내 링크 |

`open-question.yml` 필드는 문서 항목 형식과 1:1로 맞춘다 — 출처, 항목(결정해야 할 것), 상태,
해소 메모, 계열(wiki/parfait 드롭다운). **ID 필드는 두지 않는다.** ID는 문서가 부여하는
것이고, 수동 이슈는 아직 문서에 없다. 다음 `plan`에서 `unmanaged`로 잡혀 사람이 문서로 옮긴다.

템플릿에는 "정본은 문서다"라는 안내를 넣어 이슈에만 적고 끝내는 사고를 막는다.

## 스킬 `sync-open-questions`

`.claude/skills/sync-open-questions/SKILL.md`. 기존 `sync-tjyg-develop-baseline`·
`sync-teamyg-server-api`와 같은 반복 동기화 계열이다.

절차:

1. `python3 parfait/script/oq_sync.py assign-ids` 실행
2. 문서가 바뀌었으면 브랜치를 파고 로컬 커밋한다(main 직접 커밋 금지 — `CLAUDE.md`)
3. `python3 parfait/script/oq_sync.py plan --out <scratch>/oq-plan.json` 실행
4. 요약 표를 사용자에게 보고한다: create N / update M / close K / reopen J / orphan O / unmanaged U
   - `orphan`·`unmanaged`가 있으면 개별로 나열한다(자동 처리하지 않는 항목이므로)
   - 변경 0건이면 "동기 상태"로 보고하고 종료한다
5. **사용자 승인을 기다린다.** 리모트 쓰기이므로 `CLAUDE.md`의 확인 게이트에 해당한다
6. `python3 parfait/script/oq_sync.py apply <plan>` 실행
7. 결과 보고. 실패 건이 있으면 명시한다. 조용히 넘어가지 않는다

스킬은 판단을 스크립트에 위임하고, 게이트와 보고만 담당한다.

## 실행 계획

첫 실행은 112건의 이슈를 만든다(136항목 중 `해소됨` 24건 제외). `apply --limit`으로 나눠
받을 수 있게 하되 기본은 전량이다.

1. 템플릿 4종 추가
2. `oq_sync.py` + 테스트 작성
3. `assign-ids` 실행 → 136항목에 ID 부여, 로컬 커밋
4. `plan` → 사용자 승인 → `apply`
5. `parfait/script/README.md` 인덱스에 등록

## 하지 않는 것

- 이슈 → 문서 역방향 자동 반영
- TJYG-Android 저장소에 이슈 생성
- 문서 항목 요약·재작성(전문 그대로 옮긴다)
- `orphan` 이슈 자동 close
- 마일스톤·assignee 자동 배정
- CI에서의 자동 실행(사람 승인 게이트가 설계의 일부다)
